- src/client.tsx — Главная, История, Магазин (код 4 цифры), Профиль; src/api.ts — все вызовы Supabase; src/App.tsx — auth + роутинг по роли.

## Готово: годовой абонемент / 30 дней / реферал 2 000 / PWA (build ок)
- Миграция `006_annual_referral.sql` (применить в Supabase после 004, 005). Протестирована на локальном Postgres 16: годовой = ровно +10 000 (партия annual, pending), повторная продажа блокируется, реферал +2 000 только пригласившему (друг 0, повторно не начисляется), первое списание активирует партию на 30 дней (дата активации и конца сохраняются), второе списание срок не продлевает, просроченный остаток сгорает (`expire_my_bonus`, запись «сгорание» в истории).
- UI клиента: «N бонусов», «Бонусы активируются при первом использовании», «Действуют до: DD.MM.YYYY · Осталось: XX дн.», список партий «Мои бонусы», подписи в истории, реферал «+2 000 бонусов за приглашение друга». Админ: выбор «Обычный / Годовой (+10 000 Bonus)» в drawer клиента (для годового 5% не начисляется).
- PWA: public/manifest.json (start_url/scope `/formulabonus/`, standalone), иконки PNG 192/512/maskable/apple-touch, sw.js (scope-aware), регистрация через BASE_URL, vite base `/formulabonus/`, кнопка «📲 Установить Formula Bonus» (Android — beforeinstallprompt, iOS — инструкция, скрыта в standalone).

## Готово: тарифы и продление на выбранный срок (миграция 007, build ок, логика проверена на Postgres)
- Таблица `plans` (название, дни, цена, годовой?, макс. % Bonus, активен). Заглушки: 1 мес 12 000, 3 мес 30 000, 6 мес 54 000, Годовой 96 000 — ЦЕНЫ ПОМЕНЯТЬ в админке (Магазин → Тарифы абонементов).
- Клиент: «Продлить» → экран выбора срока; по умолчанию выбран его текущий тариф (по plan_id, иначе по годовой/обычный), цена, сколько спишется Bonus и «К оплате» считаются автоматически → «Получить код продления» (4 цифры).
- Админ → Списание: по коду видит «Продление: <тариф>», Bonus-скидку и сумму к оплате; кнопка «Принять оплату и продлить» одним действием списывает Bonus (FIFO, активация 30 дней) и оформляет абонемент (+5% или +10 000 для годового, реферал). Клиенты → drawer: выбор тарифа, цена подставляется (можно изменить), `sell_plan`.
- RPC: create_renewal, sell_plan, _sell (общая логика), confirm_redemption (товар или продление). Защита: годовой нельзя продлить, пока осталось >300 дней. Старый товар «Продление абонемента» скрыт.

## Готово: удаление, категории, заказы спорт-бара (миграция 008; логика проверена на Postgres 16, tsc ок, полная сборка ок)
- Админ: удаление товаров и акций (с подтверждением; «Скрыть» осталось). delete_reward — безопасно для истории (заказы/коды сохраняются, ссылки обнуляются).
- Категории товаров (таблица categories; админ добавляет/переименовывает/скрывает/удаляет; у товара поле «Категория» и «Описание»).
- Заказы: клиент собирает корзину (Магазин → категории → «В корзину»), выбирает Kaspi/Наличные и «Списать бонусы», комментарий бармену → create_order. Вкладка «Заказы» у клиента: статусы Принят → Готовится → Готов → Выдан, «Я оплатил(а)» для Kaspi, отмена пока заказ новый и не оплачен. Лимит 3 активных заказа.
- Бонусы: планируются при заказе (bonus_planned, лимит по % товара), реально списываются FIFO при подтверждении оплаты баром (bar_confirm_payment → _spend). При отмене оплаченного заказа бонусы возвращаются партией (kind adjust).
- Бар: роль `bartender` (назначает админ в «Сотрудники»), экран «Заказы бара» (3 колонки Новые/Готовятся/Готовы, звук нового заказа, переключатель «Бар открыт/закрыт», закрытые заказы); админ видит тот же экран в «Заказы бара». Выдать можно только оплаченный заказ (наличные: «Принять оплату и выдать»).
- Kaspi: РУЧНОЕ подтверждение. Клиент переводит сумму на номер из админки (Магазин → «Оплата Kaspi»), нажимает «Я оплатил(а)», бармен сверяет в Kaspi и жмёт «Принять оплату». Настоящий онлайн-эквайринг Kaspi требует договор мерчанта и серверный обработчик (Edge Function) — не сделан.
- Новые файлы: src/shop.tsx, src/bar.tsx. Применить в Supabase 004–008 по порядку.

## Готово: Checkout с Kaspi по ссылке, резерв бонусов (миграция 009; проверено на Postgres 16, tsc и сборка ок)
- Клиент: корзина → «Оформление заказа»: товары, бонусы клиента, поле «сколько бонусов использовать» (0 / Макс., лимит = % товара из админки и доступный баланс), итог «К оплате», выбор Kaspi / Наличными (скрыт, если к оплате 0). Заказ → вкладка «Заказы» со статусами по ТЗ (🟡 ожидаем оплату / подтверждения, 🟢 оплата подтверждена, 🥤 готовится, ✅ готов, ✓ выдан). Kaspi: блок с суммой, 5 шагов, кнопка «Перейти к оплате Kaspi» (ссылка из настроек), «Я оплатил». Тосты при смене статуса.
- Бонусы: при заказе РЕЗЕРВИРУЮТСЯ (orders.bonus_planned, функция _reserved; «Доступно» = партии − резерв, «Зарезервировано» показывается), окончательно списываются (_spend, FIFO, активация 30 дней) только при подтверждении оплаты. Отмена/неоплата → резерв освобождается; отмена оплаченного → возврат бонусов один раз (kind adjust).
- Статусы: orders.status = awaiting_payment → new → preparing → ready → done / cancelled; payment_status = awaiting_payment / awaiting_confirmation / cash_pending / bonus_pending / paid / cancelled; pay_method cash/kaspi/bonus; поля cash_amount, kaspi_payment_url (снимок настройки), confirmed_at, confirmed_by, client_paid_at.
- Бар/админ «Заказы бара»: колонки Ожидают оплаты / Оплачены·новые / Готовятся / Готовы; «Подтвердить оплату» (Kaspi) или «Получил оплату» (наличные); приготовление только после подтверждения; повторное подтверждение/отмена безопасны (идемпотентно).
- Защита: у клиента нет прав UPDATE на orders (RLS), клиент может только order_claim_paid («Я оплатил») и cancel_my_order (до «Я оплатил»); подтверждение только is_bar().
- Ссылка Kaspi: Админка → Магазин → «Оплата Kaspi» (settings.kaspi_payment_url). Запасной вариант: переменная VITE_KASPI_PAYMENT_URL.
- Применить в Supabase 004–009 по порядку.

## Готово: PWA-автообновление, вход по телефону, роль dev, поддержка, уведомления, день рождения (миграция 010; проверено на Postgres 16, tsc и сборка ок)
- PWA: public/sw.js получает уникальную версию при каждой сборке (vite.config.ts → плагин swVersion), страница всегда берётся с сети, хэшированные assets — из кэша, старые кэши fb-* удаляются. src/main.tsx: проверка новой версии при открытии/возврате в приложение и раз в 30 мин, одна перезагрузка после активации (не во время ввода/открытого окна, защита от циклов 15 с). localStorage/сессия Supabase не трогаются.
- Вход/регистрация по телефону (src/App.tsx, src/lib.ts): логин = технический адрес `<7XXXXXXXXXX>@phone.formula.internal` (зарезервированный домен .internal, писем не отправляется; Supabase Auth проверяет при регистрации только формат). Пароль хранит Supabase. Старые аккаунты по почте: ссылка «Регистрировались по почте? Войти по почте». Сообщение «НЕ БЕСПОКОЙТЕСЬ…», если сессия пропала не по кнопке «Выйти» (флаг fb-had-session).
- «Забыли пароль?» → request_password_reset (без входа, лимиты, одинаковый ответ) → обращение technical/password_reset у DEV → DEV «Выдать временный пароль» (dev_reset_password: bcrypt в auth.users, пароль показывается DEV один раз и нигде не хранится) → клиент входит и обязан задать новый (must_change_password, экран ChangePassword).
- Роли: добавлена dev (is_staff/is_admin/is_bar включают dev → все старые RLS-политики дают dev права admin), is_dev(). Назначать/снимать dev может только dev (set_role). «Первый пользователь = admin» теперь только если нет ни admin, ни dev.
- Поддержка (src/support.tsx): клиент — вкладка «Поддержка» (тема + описание; WhatsApp-кнопка, номер в settings.whatsapp_phone, задаётся в админке «Поддержка»). Маршрутизация в базе: «Приложение» → technical (DEV), остальные → formula (ADMIN). Таблица support_tickets: клиент видит свои, admin — formula, dev — все. Админка: раздел «Поддержка» (Новые/В работе/Закрытые, drawer, смена статуса), у dev вкладки Техника/Формула.
- Уведомления: таблица notifications (unique user_id+dedupe_key), sync_my_notifications() при открытии приложения клиентом: абонемент за 3–4 дня (ключ sub_exp:<membership>), день рождения (birthday:<год>, 29.02 → 28.02 в невисокосный). Новая акция: галочка при создании + кнопка «Уведомить» (notify_promo, promo:<id>). Бонус за друга — триггер на bonus_transactions. Колокольчик с бейджем и центр уведомлений у клиента (без realtime и постоянного опроса).
- День рождения: поле в профиле клиента (set_my_birth_date), бонус не начисляется (размер подарка не задан).
- Плашка «ОБНОВЛЕНИЕ!» для клиентов: src/whatsnew.ts (CLIENT_UPDATE.id + список). Показывается один раз на id. ПРИ КАЖДОМ ВАЖНОМ ДЛЯ КЛИЕНТОВ ОБНОВЛЕНИИ менять id и список.
